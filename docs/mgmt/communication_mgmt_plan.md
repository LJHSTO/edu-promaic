## 2. 工作入口

任务、缺陷和需求变更进入 [Issues](https://github.com/LJHSTO/edu-promaic/issues)；迭代起止日期和交付物见[迭代计划](迭代计划.md)。GitHub Projects 使用[“Edu ProMAIC 课程项目看板”](https://github.com/users/LJHSTO/projects/1/views/3)，每张卡片关联一个 Issue 或 PR，不在看板另写一份无法追踪的任务。[排期视图](https://github.com/users/LJHSTO/projects/1/views/4)按里程碑分组。

看板使用五个状态：

| 状态 | 进入条件 | 离开条件 |
|---|---|---|
| 待整理 | 尚未确定范围或验收条件 | 明确目标、优先级和负责人 |
| 待办 | 已排入迭代 | 负责人开始处理 |
| 进行中 | 正在修改文档或代码 | 提交可评审的变更和验证结果 |
| 待评审 | 已有提交或 PR，待检查 | 验收通过并合入主分支；未通过则退回进行中 |
| 已完成 | 变更已入主分支，验收结果可查 | 发现回归问题时新建缺陷并关联原任务 |

每人同时进行中的任务最多 2 项。GitHub 的系统字段（Status、Assignees 等）保留原名，状态选项与项目说明使用中文。#8、#9 的 Assignees 按第 1 节分工设置，LJHSTO 保留跟踪。

## 3. 计划、同步与评审

采用两周一个迭代。每周进行一次约 20 分钟的进度同步，具体时间由成员确认，不虚构已经召开过的会议。同步以看板“进行中”列为材料，每人说明完成项、阻塞项和下一步，结果作为评论写入对应 Issue；需要讨论的设计也放到关联 Issue，形成可追踪的决定。迭代评审查看 Milestone 进度条（已关闭 / 总数），复盘要点记录在专门 Issue 并归档到 `docs/retrospection/`。

关闭 Issue 前确认验收条件、文档链接、相关测试和提交记录。需求评审的决定写回对应任务。

每轮评审展示可运行演示、需求到测试的对应关系和下一步安排。复盘记录进入 `docs/retrospection/`。

## 4. 缺陷处理

缺陷用中文表单提交，至少包含环境、复现步骤、预期与实际结果、优先级。统一标签为 `bug`、`priority:P0/P1/P2`；其他任务按 `documentation`、`requirements`、`enhancement` 分类。

- P0：保护状态被绕过、真实数据泄漏或主要流程完全不可用，先止损再处理。
- P1：影响常用功能，当前迭代优先修复。
- P2：有可用替代操作或轻微显示问题，按迭代容量安排。

处理流程是确认复现、指定负责人和里程碑、修复、运行针对性验证、复查。提交或 PR 使用 `Fixes #编号` 关联已完整解决的事项；部分完成使用 `Refs #编号`，不提前关闭。看板状态更新需要核实实际合并和验收结果，不把所有“已关闭”都当成“已完成”——重复事项应保留说明。

## 5. 完成定义与变更

代码和文档进入 `main`，相关检查通过，需求、接口和使用说明一致，且不存在未注明的验收缺口，才算完成。涉及真实课堂的条目还需教师内容审核、数据处理说明及试用同意。

新增需求先记录影响到的 FR / NFR 编号，再讨论是否进入迭代。组员无需为了小改动另走一套审批，但不能在文档中把计划或假设写成实测成果。

看板、里程碑和任务记录见[协作流程](协作流程.md)。
