# 第三周交付后的 Scrum 配置复盘

日期：2026-11-04。依据仓库和公开 Projects 实际检查整理，不代表已经召开团队 Retro 或课堂评审。

## 事实与结果

第三周 10 个用户故事、交互原型、技术方案和两周学习计划经 PR #10 合入 main。本地 20 项测试及该 PR 的四组 Windows/Linux、Node.js 22/24 检查通过；教师确认和 320px 补验仍待进行。

再次按课件第 40–43 页检查时，Projects 仍只有 #1/#2/#3/#5/#6 五张历史完成卡，没有 #7/#8/#9；新计划 Issue #8/#9 也没有负责人或 Milestone。这表明“文档和代码已提交”没有保证“协作看板已同步”。

本轮实际补齐 #7 的负责人和 Milestone #2、#8/#9 的负责人和 Milestone #3；将剩余配置缺口记录为真实缺陷 #11，标 `bug`、`priority:P2`，设置负责人和 Milestone #2。未完成的学习任务保持开放。

用户登录后，同日补入 #7/#8/#9/#11，在 Table 核对全部 9 张 Issue 卡；确认 Item closed 和 Pull request merged 均 On → 已完成，并启用仓库开放 Issue 自动入板。项目启用的工作流从 6 条增至 7 条。#8/#9 仍为待办，#11 随本次修复 PR 完成闭环。

## 原因与改进

先前交付检查覆盖代码、文档和 PR，没有把 Projects 卡片同步列入完成检查。自学计划中的子目标与 GitHub Milestones 也没有明确对应。公开页面不能显示可确认的 Workflows 设置，不能把历史配置说明直接当作本轮验证。

| 行动 | 跟踪责任 | 检查条件 | 当前状态 |
|---|---|---|---|
| 当前任务补负责人和真实 Milestone | LJHSTO | #7/#8/#9/#11 元数据可查 | 已实际修改 |
| 补当前卡片、核对关闭/合并自动移列 | LJHSTO | 五列中包含当前工作，Workflows 有可核验记录 | 9 张 Issue 卡已核对，两个规则均 On → 已完成 |
| 新 Issue 进入看板，防止再次遗漏 | LJHSTO 组织认领 | Auto-add 或实际人工补录；新增后复查 | Auto-add 已保存并开启，筛选本仓库开放 Issue |
| 保留部分修复的未完成状态 | PR 提交者与维护者 | 部分处理用 Refs，完整修复才用 Fixes | PR #12 使用 Refs；补齐配置后的关联修复 PR 使用 Fixes |

完整配置、逐页证据和合并闭环见[第 40–43 页核验](../mgmt/github_scrum_audit.md)。本轮补的是实际协作设置，没有据此声明未来 PoC、团队会议或课堂试用已完成。
